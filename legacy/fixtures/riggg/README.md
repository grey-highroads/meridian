# Riggg Fixture

> Status: Journey definition. Synthetic assets and contracts remain to be added.

## Product purpose

Test whether the system can help a producer create approved variations from explicit canon without reinterpreting locked geometry, palette, roles, or relationships.

This is a product-journey proof first and a fidelity fixture second.

## User and context

The primary user is a brand-production operator creating a new deliverable from an established visual system. Approved assets and rules exist, but the task still requires selecting the correct source material, applying bounded variation, evaluating fidelity, and revising without collateral changes.

The operator wants the deliverable completed correctly. They should not need to choose an architectural mode, inspect prompts, or understand provider routing.

## Desired outcome

- Correct approved assets are resolved automatically.
- Locked geometry and relationships remain exact.
- Permitted variation is clear in the language of the deliverable.
- Drift and unrequested changes are caught before approval.
- Revisions preserve everything the user did not ask to change.
- The job retains a complete audit trail without burdening the operator with metadata entry.

## Journey

1. **Choose the deliverable workflow.** The operator selects a named adaptation or production workflow.
2. **Provide the brief.** They choose the target format, source character or asset set, requested change, and delivery context.
3. **Resolve exceptions.** The system finds applicable canon and shows only missing, contradictory, or unsupported requirements.
4. **Run constrained production.** The configured stage applies deterministic composition and bounded transformations.
5. **Review findings.** The operator sees specific drift or completeness failures attached to affected elements.
6. **Request a targeted revision.** The request names the change and protected non-changes.
7. **Approve and package.** The workflow approver authorizes the output; job memory records the result without changing canon.

## User decisions

- Which named deliverable and source variant are required?
- How should an unsupported exception be resolved?
- Is a flagged relationship acceptable or does it require revision?
- Is the corrected output approved for its intended scope?

The user should not select a constrained preset. The workflow's production stage already uses constrained policy configuration.

## Automatic workflow decisions

- exact canonical asset versions and applicable relationships;
- locked and bounded handling;
- deterministic tools and integrity checks;
- drift-first evaluation order;
- revision steps that can be safely reused;
- appropriate approval route.

## Failure and recovery path

The fixture must include a missing canonical asset and an output with one unrequested geometry change. Missing canon blocks preflight with a resolvable explanation. Drift blocks approval and produces a targeted revision that preserves all unaffected elements.

## Required fixture artifacts

- synthetic registered assets and integrity metadata;
- canonical identity and production entities;
- named deliverable workflow and constrained stage definition;
- production request, context manifest, and stage policy snapshot;
- deterministic execution plan and artifact lineage;
- drift evaluation, targeted revision, and approval event;
- failure cases for missing canon and unrequested change;
- internal hybrid control snapshot using the same brand-brain slice where appropriate.

No real client-confidential material may be committed. Inputs and expected outputs must be synthetic or sanitized.
