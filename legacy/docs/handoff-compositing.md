# Handoff: deterministic text compositing

- Written: 2026-08-10
- Status: not started, not scheduled
- Governing decision: ADR 0014, revision of 2026-08-10
- Prerequisite: an ADR resolving build-or-integrate, described below. Do not start the compositor before that exists.

This document exists so a future session can pick up the compositing question without relitigating what has already been decided. It records the decision, the open question, what the system already provides, and what would still have to be built.

## What was decided, and why it is not reopenable

Generated in-image copy is rejected permanently. Not deferred, not gated. Three reasons, all recorded in the ADR revision:

The renderer fidelity gate was retired without being run, because it measured string fidelity in isolation and the actual requirement is text plus layout, correct predictably and repeatably across every placement the product serves. A pass would not have licensed the feature.

A probabilistic guarantee on exact claim language is a different category from a guarantee, not a weaker version of one. The product's stated differentiator is that discipline is enforced in schema and compiled artifacts rather than left to model judgment. Model-drawn claim text is model judgment at any hit rate.

Layout is not this product's competence. The system is built to excel at world building, and the ADR had already rejected system-typeset documents on the grounds that layout tools are better at layout. Part two as originally drafted reversed that quietly.

A future session should not reopen these on the basis that text rendering has improved since. Improvement in rendering does not change any of the three arguments, because none of them is about the current hit rate.

## The open question, which must be answered first

**Does the compositor live inside this system, or does the system hand off to a tool that already does layout?**

The distinction that matters is scope, not technology:

*Simple compositing.* Approved text typeset at a known position, in a known type style, onto a text-free render. One text block, one anchor, predictable output. This is bounded and sits inside the product's lane.

*General layout.* Multiple elements, arbitrary formats, flowing text, responsive positioning, user-adjustable composition. This is a layout tool. Building it inside this system reintroduces exactly the competence problem the ADR revision was written to avoid.

The trap is that the first grows into the second one requirement at a time. Whatever the decision, it should name the line and say what is explicitly out.

Considerations for whichever session takes this on:

- For slides specifically, the destination is usually PowerPoint or Figma, and reps already work there. Handing off a governed image, governed copy, and a placement contract may serve that better than compositing in-system.
- For social, there is no downstream layout tool in the workflow. A caption is text beside an image, not on it, so social may not need a compositor at all.
- The strongest case for in-system compositing is the one described in the 2026-08-10 conversation: a slide with a strong image and an approved value statement baked into the element, generated by a rep who is not a designer. That case wants exactly one text block on one image, which is the bounded version.

## What the system already provides

Verified by reading the code as of 2026-08-10:

**Governed copy exists and is audited.** `src/copy/types.js` is the catalog; `src/copy/generate.js` produces a block with text and a normalized audit. A `headline_set` type is sequenced but not built, and it is the type a compositor would consume, since display copy is short lines rather than prose.

**The claims spine gives exact strings.** Approved claim language is preserved verbatim through `src/claims/assembly.js`. This is the thing that must not be redrawn.

**The compiled package is the durable record.** `src/production/package.js` writes a per-job package carrying the copy contract, and `writeOutputPackage` persists it. A composited output would need its text layer recorded there for the same reason: past outputs must stay reviewable with the exact string that was placed.

**The treatments model already expresses locked elements with exact fidelity.** ADR 0014 part two specified that in-image copy participates as a locked element. That mechanism exists for protected assets and would carry over.

**Universal text safety stays in force.** `src/production/prompt-craft.js` keeps text out of renders. A compositor depends on this rather than superseding it: the render must be reliably text-free for text to be placed onto it. Do not weaken this rule.

**Deterministic prose checking exists.** `src/copy/prose-check.js` is string-matched and has no false positives. Anything composited should pass it before placement, since a rendered mistake is not correctable in the way a caption is.

## What is not built

**REASONED, not verified. None of the following has been prototyped, and the effort estimates are inference from the existing placement path rather than from reading compositing code, because there is none.**

- Any image manipulation capability. There is no canvas, no font pipeline, no text measurement. The runtime is Node on Vercel Hobby, and font rendering in that environment is its own investigation.
- A text-free render mode. Current renders are not guaranteed to leave usable negative space. Composing onto an image that was not composed for text produces bad results, so the brief likely has to ask for space, and that is a prompt and treatments change.
- Any representation of position, type style, or safe area. There is no schema for where text goes.
- Anything in the UI. No preview, no adjustment, no approval of a composited result as distinct from its parts.

## Hard constraints that will still apply

- **The function count is at 12 of 12** on Vercel Hobby. Any new operation dispatches through an existing handler via an `action` field. A compositor doing image work in a serverless function will also meet payload and execution limits worth checking before design.
- **`src/compiler.js` and `schemas/v1/` are frozen.**
- **Compile-time changes must be tested against every placement shape.** `test/copy-contract.test.js` has the parity harness; extend it rather than writing a new one. A regression on 2026-08-09 came from testing one placement.
- **Cold-start empty state is required.** A client with no claims and no products must flow through.
- **No em dashes anywhere.**

## Related open items

- **The homepage claim "placed directly, never regenerated" is unsupported** by the live implementation, which uses model-based asset placement. A compositor would make it true for copy, not for asset placement. Do not let the two merge in marketing copy.
- **The claims admin screen does not exist.** The segment axis shipped 2026-08-10 and is unusable from the app for the same reason. Compositing would add another thing configured only at the store level.
- **`headline_set` is unbuilt** and is the natural prerequisite: there is no display copy to composite until the catalog produces it.
